# Committee System Guideline

This guideline explains how to create and manage committees in the NDM system.

## Purpose

The committee module supports a strict hierarchy from central to union level.

## Committee Hierarchy

Use committee type hierarchy order to define structure:

1. Central Committee (order 1)
2. Division Committee (order 2)
3. District Committee (order 3)
4. Upazila Committee (order 4)
5. Union Committee (order 5)

## Parent Committee Rules

Parent selection must follow one-level-up mapping only:

- Central committee: no parent allowed
- Division committee: parent must be central committee
- District committee: parent must be division committee
- Upazila committee: parent must be district committee
- Union committee: parent must be upazila committee

Additional protection rules:

- A committee cannot be its own parent.
- Cyclic hierarchy is not allowed.
- A parent with active children cannot be deleted.

## Location Rules By Committee Type

Location IDs are required according to committee level:

- Central: no location required
- Division: division_id required
- District: division_id + district_id required
- Upazila: division_id + district_id + upazila_id required
- Union: division_id + district_id + upazila_id + union_id required

## Required Create Payload (Minimum)

```json
{
  "name": "Dhaka District Committee",
  "committee_type_id": 3,
  "parent_id": 12,
  "status": "active"
}
```

Notes:

- `slug` is auto-generated from name if not provided.
- `is_current` defaults to true if not provided.
- `code` is auto-generated by committee type prefix and serial.

## Auto Committee Code Format

Committee code is auto-generated in this format:

- Central: `CEN-01`, `CEN-02`, ...
- Division: `DIV-01` to `DIV-08` (as needed)
- District: `DIS-01` to `DIS-64` (as needed)
- Upazila: `UPA-01`, `UPA-02`, ...
- Union: `UNI-01`, `UNI-02`, ...

The system increments serial per committee type automatically.

## Mandatory Creation Sequence

Creation must follow hierarchy order:

1. Create Central committee first.
2. Then create Division committees under Central.
3. Then create District committees under Division.
4. Then create Upazila committees under District.
5. Then create Union committees under Upazila.

If upper-level parent type committee does not exist, lower-level creation is blocked.

## Common Validation Errors

- `parent_id`: invalid hierarchy mapping for parent and child type
- `parent_id`: parent required for non-central committee
- `parent_id`: central committee cannot have parent
- `parent_id`: cyclic hierarchy detected
- duplicate scope error: same name + type + location already exists

## UI Behavior Guideline

For create/edit forms:

- Use dropdown for committee type (not free text ID).
- Use dynamic parent dropdown filtered by valid parent type.
- Use cascading location selectors:
  - Division -> District -> Upazila -> Union
- Reset child selectors when parent location changes.

## Recommended Admin Workflow

1. Create committee types with correct hierarchy order.
2. Create central committee first.
3. Create lower-level committees from top to bottom.
4. Keep status and current term updated.
5. Review tree view after changes.

## API Filter Guideline

Use ID-based filters for consistency:

- committee_type_id
- parent_id
- division_id
- district_id
- upazila_id
- union_id
- status
- is_current

## Security and Data Quality Notes

- Do not enter random numeric IDs manually.
- Always prefer selector-based UI for IDs.
- Keep hierarchy and location data aligned before approving records.

## Fully Automated Setup Suggestions

These suggestions help run committee setup and maintenance with minimal manual work.

### 1. One-Command Environment Bootstrap

Create a bootstrap command that runs in order:

1. Migrations
2. Seed committee types
3. Seed central and division committees
4. Run post-seed validation

Recommended sequence:

```bash
php artisan migrate --force
php artisan db:seed --class=CommitteeTypeSeeder --force
php artisan db:seed --class=DivisionCommitteeSeeder --force
php artisan app:validate-committee-hierarchy
```

### 2. Add a Dedicated Hierarchy Validation Command

Add an Artisan command such as `app:validate-committee-hierarchy` that checks:

- parent committee type is exactly one level above child type
- no self-parent or cyclic parent relation
- required location fields exist by hierarchy order
- duplicate scope (same name + type + location) does not exist

Use this command in deployment and CI.

### 3. Nightly Automated Data Health Check

Schedule a nightly job in Laravel Scheduler that:

- runs hierarchy validation
- flags committees with invalid parent/location mapping
- writes summary report to logs or database
- sends alert to admin email or notification channel

### 4. CI Gate for Committee Integrity

In CI pipeline, fail build if committee integrity checks fail:

```bash
php artisan test --filter=Committee
php artisan app:validate-committee-hierarchy
```

This prevents broken parent_id or location data from reaching production.

### 5. Automate Parent Option Safety in UI

Keep form behavior fully automated:

- parent dropdown auto-loads by selected committee type order
- parent field auto-clears when selected type changes to central
- invalid stale parent_id values auto-reset before submit

### 6. Seed-Based Rollout for New Regions

When administrative geography changes, use seeders to generate required committees instead of manual entry.

Recommended approach:

1. Add/refresh geography master data
2. Run region-aware committee seeder
3. Run hierarchy validator
4. Export post-run summary

### 7. Operational Monitoring Metrics

Track these metrics for automation quality:

- total committees by hierarchy level
- committees with missing parent_id where required
- committees with missing required location IDs
- committees blocked from delete due to active children

Add these to admin dashboard alerts for early detection.
